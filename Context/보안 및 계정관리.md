# 보안 및 계정관리

## 1. 목적과 적용 범위

이 시스템은 개인정보와 민감정보가 포함될 수 있는 HWPX·PDF 원본, 추출문, 검색 색인·임베딩, 사용자 질문·답변·평가, 평가 Excel, 로그와 백업을 다룬다. 실제 자료는 Windows 11 폐쇄망 서버에서만 생성·보관하며 외부 개발 PC와 GitHub로 반출하지 않는다.

현재 계획의 품질 개선은 문서 검색과 답변 설정 조정을 중심으로 하며 모델 가중치 추가 학습은 포함하지 않는다. 그러나 RAG 문서, 임베딩과 사용자 피드백도 원문에서 파생된 민감한 운영 자료로 보고 같은 보호 기준을 적용한다.

보안은 암호화 한 가지에 의존하지 않는다. 계정 인증, 최소 권한, 저장·전송 암호화, 키 분리, 실행 프로그램 통제, 감사 기록, 백업과 사고 대응을 여러 겹으로 적용한다. 폐쇄망이라는 이유만으로 내부 사용자, 악성코드, 반입 매체, 물리적 탈취와 관리자 계정 침해 위험이 사라지는 것으로 보지 않는다.

## 2. 계정 관리 제안

### 2.1 우선안과 대안

기관에서 Active Directory 등 기존 사내 계정을 운영한다면 그 계정과 연동하는 방안을 우선 제안한다. 퇴직·전보에 따른 계정 회수와 기관의 기존 인증 정책을 재사용하고, 이 시스템이 사용자 비밀번호를 별도로 보관하지 않기 위해서다. 구체적인 연동 방식은 폐쇄망의 계정 인프라와 Windows 11 운영 정책을 확인한 뒤 결정한다.

기존 계정 연동이 불가능하면 시스템 전용 계정을 사용한다. 사용자의 임의 가입은 허용하지 않고 관리자가 승인·생성·비활성화한다. 비밀번호는 복호화 가능한 값으로 저장하지 않고 솔트와 충분한 비용 계수를 적용한 검증된 비밀번호 해시로 저장한다. 로그인 실패 횟수 제한, 잠금, 세션 만료, 비밀번호 재설정과 계정 회수 절차를 둔다. 관리자에게는 기관 환경에서 사용 가능한 다중인증 또는 보안키 적용을 우선 검토한다.

공용 관리자 계정은 사용하지 않는다. 모든 관리 작업은 개인별 관리자 계정으로 수행해 누가 변경했는지 확인할 수 있게 한다. 퇴직·전보·업무 변경 시 계정을 즉시 비활성화하고 권한을 회수하며, 계정과 권한 목록을 정기적으로 검토한다.

### 3.1 디스크 암호화

Windows 11 서버의 OS, PostgreSQL 데이터, 원본, 평가자료, 로그와 백업이 저장되는 볼륨에 BitLocker를 적용하는 것을 우선 제안한다. TPM과 Secure Boot 상태를 확인하고 복구키는 서버 내부나 같은 백업 디스크에 두지 않고 기관이 승인한 별도 위치에 보관한다.

TPM만 사용하면 재부팅 후 자동 운영과 결합하기 쉽지만, 서버가 정상 부팅된 뒤 침해되면 암호화가 접근을 막지 못한다. TPM과 시작 PIN을 함께 사용하면 물리적 탈취 방어는 강해지지만 재부팅 때 사람이 필요해 현재의 무인 자동 시작 요구와 충돌한다. 서버실 출입 통제와 자동 복구 필요성을 함께 검토해 둘 중 하나를 확정한다.

### 3.2 애플리케이션과 DB 데이터

BitLocker는 디스크를 분리하거나 서버가 꺼진 상태에서 탈취하는 위험을 줄이지만, 실행 중인 앱·관리자 계정이 침해된 상황까지 해결하지 못한다. 특히 보호 필요성이 높은 원문 질문이나 식별정보에는 애플리케이션 수준의 인증된 암호화를 추가 적용할 수 있다. 적용할 경우 알고리즘과 라이브러리는 기관 보안 기준에 맞춰 확정하고, 암호화 키를 DB와 분리한다.

임베딩을 개별 암호화하면 pgvector의 유사도 검색과 색인 사용이 어렵다. 임베딩은 익명 정보로 간주하지 않고 BitLocker, DB 접근 통제, 로컬 전용 DB 연결과 외부 반출 금지로 보호한다. 원본·추출문·검색 색인·임베딩의 보호 수준과 재생성 가능 여부를 기록한다.

PostgreSQL은 앱 전용 계정과 관리 계정을 분리한다. `trust`와 MD5 인증은 사용하지 않고 `SCRAM-SHA-256`을 적용한다. PostgreSQL과 Ollama는 서버의 로컬 주소에서만 접근하게 하며 일반 사용자 PC에 DB·Ollama 포트를 개방하지 않는다.

### 3.3 비밀값과 키 관리

공통 문서 암호, DB 비밀번호와 데이터 암호화 키는 Git, 소스 코드, `release/`, 일반 설정 파일, 로그와 DB 데이터 안에 직접 저장하지 않는다. Windows 서비스 계정에 묶인 DPAPI 보호 파일이나 기관이 승인한 Windows 인증서 저장소 등으로 보호하고, 필요한 서비스와 관리자만 접근하게 한다.

암호화 키, BitLocker 복구키와 백업 복호화 키는 보호 대상 데이터와 같은 위치에 두지 않는다. 키 발급·교체·폐기·분실 복구 절차와 담당자를 정하고, 키를 로그나 오류 화면에 출력하지 않는다. 키 교체 후 기존 자료를 어떻게 다시 암호화할지도 시험한다.

## 4. 전송과 웹 보안

내부망에서도 웹은 기관 내부 인증기관이 발급한 인증서로 HTTPS를 적용한다. 로그인 세션 쿠키에는 `Secure`, `HttpOnly`, `SameSite` 속성을 적용하고, 세션 만료와 로그아웃 시 무효화를 구현한다. 상태를 변경하는 요청은 CSRF 방어를 적용하고 입력값 검증, 업로드 형식·크기 제한과 오류 메시지의 민감정보 제거를 수행한다.

Windows 방화벽은 확정된 웹 포트만 허용된 내부망 주소 대역에 개방한다. 원격 관리는 원칙적으로 끄거나 별도의 관리자 대역과 승인된 관리자에게 제한한다. 서버의 공유 폴더로 원본·백업을 일반 사용자에게 노출하지 않는다.

## 5. 서버와 악성코드 방어

- Windows 보안 업데이트와 NVIDIA·Python·PostgreSQL·Ollama·의존성 보안 업데이트는 외부망에서 검증하고 승인된 오프라인 절차로 반입한다.
- Microsoft Defender 실시간 보호를 유지하고 데이터·백업 폴더에 보호된 폴더 기능 적용을 검토한다.
- App Control for Business를 우선 검토해 승인된 앱·스크립트만 실행하도록 한다. 처음에는 감사 모드에서 필요한 실행 파일을 확인한 뒤 차단 모드로 전환한다.
- 앱 서비스는 Windows 관리자 권한이 없는 전용 계정으로 실행하고 대화형 로그인을 금지한다.
- 반입 설치 파일·모델·문서는 승인, 악성코드 검사, 파일 목록과 SHA-256 대조를 거친다.
- 사용하지 않는 서비스·포트·공유를 끄고 서버실 출입과 반입 매체를 통제한다.

## 6. 백업과 보존·삭제

백업은 운영 데이터와 다른 저장 장치 또는 위치에 두고 별도로 암호화한다. 백업 복호화 키는 백업과 분리해 보관한다. 랜섬웨어나 관리자 실수로 운영 데이터와 백업이 함께 삭제되지 않도록 쓰기 권한과 연결 시간을 제한하고, 정기적으로 실제 복구 시험을 수행한다.

관리자가 사용자 질문·답변 데이터의 보존 기간을 설정할 수 있고, 보존 기간이 지나면 선택하여 삭제하거나 익명화할 수 있도록 한다. 운영 DB뿐 아니라 로그와 백업에서의 만료·삭제 방식도 기관 정책에 맞춰 확정한다. 익명화한 자료는 다시 개인을 식별할 수 있는 값이 남지 않았는지 검증한다.

## 7. 감사 기록

다음 사건을 감사 기록으로 남긴다.

- 로그인 성공·실패, 계정 잠금과 비밀번호 재설정
- 계정 생성·비활성화와 역할·권한 변경
- 원문·질문·답변·평가자료의 관리자 조회와 내보내기
- 문서 등록·교체·삭제, 평가 승인·반려와 튜닝 설정 변경
- 보존 기간 변경, 삭제·익명화 실행, 백업·복구와 배포
- 방화벽·보안 설정 변경과 반복되는 오류

감사 로그에는 비밀번호, 암호화 키, 문서 공통 암호와 필요 이상의 질문 원문을 남기지 않는다. 로그 열람 권한과 보존 기간을 제한하고 관리자 본인의 행위도 기록한다. 가능하면 운영 DB와 다른 보호 위치에 사본을 남겨 앱이나 DB가 침해되었을 때 임의 삭제 여부를 확인할 수 있게 한다. 접속기록은 정기적으로 점검하고 이상 징후에 대한 담당자와 조치 절차를 정한다.

## 8. 침해 대응과 복구

침해가 의심되면 다음 순서로 대응한다.

1. 서버와 관련 계정을 격리하되 전원을 즉시 끄기 전에 로그와 증거 보존 필요성을 판단한다.
2. 영향받은 계정·비밀번호·인증서·암호화 키의 사용을 중단하고 교체한다.
3. 원본, DB, 로그, 백업과 반입 이력을 이용해 노출·변조·삭제 범위를 확인한다.
4. 검증된 설치 자료와 깨끗한 환경에서 복구하고 백업 무결성을 확인한다.
5. 재개 전에 계정, 권한, 방화벽, 실행 허용 목록, 데이터와 모델 해시를 다시 검증한다.
6. 기관 개인정보 보호·보안 담당자에게 보고하고 관련 법령과 기관 절차에 따른 신고·통지 여부를 판단한다.

담당자 연락망, 서버 격리 방법, 증거 보존, 백업 복구, 서비스 재개 승인과 사후 보고 양식을 운영 전에 마련하고 모의 훈련한다.
