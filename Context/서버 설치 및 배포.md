# Windows 11 서버 최초 설치 및 배포

## 1. 적용 범위와 현재 상태

이 문서는 Windows 11 PC 한 대에 CaseSearch를 설치하고, 이후 필요한 결과물만 복사해 갱신하는 절차를 정한다. 운영 사용자는 내부망에서 접속하며, 질문은 여러 건 접수해도 AI 답변은 서버 전체에서 동시에 1건만 처리한다.

개발 PC와 GitHub는 외부망에 있고 실제 서버는 인터넷이 없는 폐쇄망에 있다. 개발 PC에서는 공개 문서 또는 가상 시험 자료를 저장소 밖의 별도 데이터 폴더에 두고 사용한다. GitHub에는 소스 코드, 정적 화면, 비밀값 없는 설정 예시와 공개 가능한 설계 문서만 올린다. 제한된 원본 문서와 그 추출문·임베딩, 실제 질문·답변·피드백, 평가 Excel, 운영 로그·백업은 폐쇄망에서 생성·보관하며 외부망으로 반출하지 않는다. 현재 계획에는 모델 가중치 추가 학습이 없고, 이 문서에서 말하는 튜닝 자료는 주로 서버 DB의 운영 기록이다.

현재는 설계 단계다. 실제 프로그램, `release/` 묶음, 설치 스크립트, DB 변경 파일은 아직 만들어지지 않았다. 아래 제품과 모델은 `design.md`의 우선 제안이며 설치 전 버전·호환성·실측 결과로 확정한다. 경로와 버전명은 예시이고 서버의 저장 공간을 확인한 뒤 고정한다.

## 2. 복사할 것과 서버에 남겨둘 것

개발 PC에서 웹 화면과 서버 프로그램을 하나의 `release/` 폴더로 묶는다. 저장소의 `docs/`에는 웹 화면 결과물을 두고, 배포할 때 그 내용을 `release/docs/`에 포함한다. 프로젝트 규칙에 따른 GitHub의 `docs/` 배포 설정과 관계없이 실제 운영 화면과 `/api`는 서버 PC의 FastAPI가 내부망에 제공한다.

`docs/`만 복사하면 화면 파일만 옮겨진다. 질문 접수, 검색, DB·Ollama 연결, 문서 등록, 대기열과 평가 기능을 실행하려면 `app/`, `docs/`, DB 변경 파일, 의존성 목록과 실행 자료가 함께 든 `release/` 전체가 필요하다. 개발 PC에서는 이를 Git 추적 대상 밖의 전송 폴더에 만들고, 폐쇄망 서버에는 승인된 매체로 반입한다. GitHub Pages를 쓰더라도 그곳에는 공개 가능한 정적 화면만 게시하며 실제 운영 데이터나 폐쇄망 API 주소를 넣지 않는다.

```text
개발 PC: release/                         Windows 11 서버: C:\CaseSearch\
  app/        API·검색·등록·작업자             releases\<버전>\  ← release/ 전체 복사
  docs/       웹 화면                         data\incoming\    ← 신규 HWPX·PDF
  migrations/ DB 구조 변경 파일               data\originals\   ← 등록된 원본
  requirements.txt  Python 의존성             data\evaluation\  ← 향후 승인 Excel
  실행 파일·설정 예시                         config\            ← 운영 설정·비밀값
                                            backups\           ← 백업
                                            logs\              ← 운영 로그

별도 설치: PostgreSQL·pgvector, Ollama·모델, Python, NVIDIA 드라이버
```

`release/`에는 운영에 필요한 코드와 정적 웹 파일, 의존성 목록, DB 변경 파일, 실행 설명, 비밀값이 없는 설정 예시만 담는다. 원본 문서, DB 데이터, 사용자 질문·답변, 승인된 평가 Excel, 모델 저장소, 암호와 실제 운영 설정은 복사 묶음에 넣지 않는다. 새 버전을 복사해도 이 데이터는 유지되어야 한다. Python `.venv`도 PC 간에 복사하지 않고 서버에서 만든다.

### 2.1 외부망에서 준비할 오프라인 반입 묶음

| 위치 | 허용하는 내용 | 금지하는 내용 |
| --- | --- | --- |
| 외부망 개발 PC의 저장소 밖 데이터 폴더 | 공개·가상 샘플과 그 시험 산출물 | 폐쇄망 운영 자료의 저장, 샘플·시험 산출물의 Git 추적 또는 `release/` 포함 |
| GitHub | 소스, `docs/` 정적 화면, 비밀값 없는 설정 예시, 공개 가능한 설계 문서 | 공개·가상 샘플을 포함한 모든 샘플, 시험 DB·색인·임베딩·질문·답변·평가·로그·백업·암호 |
| 외부망의 전송 폴더 | `release/` 전체, Windows 11용 설치 파일, Python 패키지 묶음, 검증된 공개 모델 파일, 파일 목록·SHA-256 값 | 실제 운영 데이터, 서버에서 복사해 나온 파일 |
| 폐쇄망 서버 | 반입·검증된 프로그램과 설치 파일, 실제 원본·DB·평가 Excel·운영 기록·백업 | 인터넷에서 직접 내려받는 설치 절차, 운영 자료의 외부 반출 |

최초 설치용 전송 폴더에는 NVIDIA 드라이버, Windows용 Python·PostgreSQL·Ollama 설치 파일, PostgreSQL 버전에 맞는 pgvector 설치 수단, Python `wheelhouse/`, 로컬 등록 가능한 답변·임베딩 모델 파일을 준비한다. PostgreSQL·pgvector 묶음은 실제 서버와 동일한 Windows 11·PostgreSQL 주 버전·아키텍처의 시험 환경에서 설치, 확장 생성, 임베딩 저장·유사도 검색, 백업·복원을 먼저 검증한다. 이후 버전에서는 변경된 항목만 다시 반입할 수 있다. 패키지 버전·파일명·SHA-256 목록을 작성하고 기관의 승인·악성코드 검사 절차를 거친 뒤 서버에서 해시를 다시 확인한다. 반입 매체를 통해 폐쇄망 데이터를 개발 PC로 되가져오지 않는다.

GitHub에 올리기 전에는 변경·추적 파일 목록과 `docs/` 내용을 직접 점검한다. `.gitignore`는 실수 방지 수단으로 보완하되, 이미 추적된 파일이나 Git 이력의 민감 자료를 지우는 기능으로 간주하지 않는다. 전송 폴더는 저장소 바깥에서 만들고, 폐쇄망 서버에 반입한 설치 자료는 운영 데이터와 분리해 보관한다.

## 4. Windows 11 최초 설치 순서

### 4.1 GPU와 Python

1. 외부망에서 RTX 5060과 Windows 11에 맞는 NVIDIA 드라이버 설치 파일을 준비해 승인된 방식으로 반입한다. 서버에서 설치·재시작한 뒤 PowerShell의 `nvidia-smi`로 GPU 인식과 드라이버 상태를 확인한다.
2. 개발·배포에서 사용할 동일한 Python 버전을 정하고 Windows 설치 파일을 반입한다. 서버에 설치한 뒤 `py --version` 또는 `python --version`으로 확인하고, 복사한 각 앱 버전 폴더에 `.venv`를 새로 만든다.
3. 외부망의 Windows 11·Python 호환 환경에서 `requirements.txt`의 고정 버전에 맞는 패키지 파일을 `wheelhouse/`에 모두 준비한다. 서버에서는 `--no-index --find-links`로 이 로컬 묶음만 사용한다. `.venv`는 복사·반출하지 않고 같은 의존성 목록으로 재생성한다.

### 4.2 PostgreSQL과 pgvector

1. 승인된 Windows용 PostgreSQL 오프라인 설치 파일로 설치한다. DB 데이터 폴더의 위치를 정하고, 앱 전용 DB와 앱 전용 계정을 만든다. 앱은 PostgreSQL 관리자 계정으로 접속하지 않는다.
2. PostgreSQL의 주 버전·Windows 아키텍처에 맞는 pgvector 설치 수단을 외부망에서 준비한다. 공식 Windows 안내의 Visual Studio C++ 빌드 도구가 필요하다면 그 도구의 오프라인 설치 가능 여부와 기관 사용 조건도 확인한다. 폐쇄망에서 `git clone`이나 온라인 패키지 설치를 전제로 하지 않는다. 서버와 동일한 Windows 11 시험 환경에서 설치와 기본 동작을 사전 검증한 묶음만 반입하며, 실제 서버에서는 설치 가능 여부를 처음 판단하는 것이 아니라 반입 파일의 무결성, 확장 생성과 실제 검색·백업·복원 동작을 최종 확인한다.
3. 앱 DB에서 `CREATE EXTENSION IF NOT EXISTS vector;`를 실행하고 `SELECT extversion FROM pg_extension WHERE extname = 'vector';`로 확인한다. DB 구조는 향후 `release/migrations/`의 승인된 변경 파일로 적용한다.
4. PostgreSQL은 같은 PC의 앱에서만 접속하도록 로컬 주소에 바인딩한다. DB 포트를 일반 웹 사용자에게 개방하지 않는다.

### 4.3 Ollama와 모델

1. 승인된 Windows용 Ollama 오프라인 설치 파일로 설치하고 `ollama --version`으로 확인한다. 모델 저장 위치를 별도 디스크로 옮겨야 한다면 등록 전에 `OLLAMA_MODELS` 환경변수를 정한다.
2. 폐쇄망 서버에서는 `ollama pull`을 사용하지 않는다. 외부망에서 공개 모델의 로컬 파일(GGUF 또는 지원되는 Safetensors)과 필요한 `Modelfile`을 준비하고, 동일한 Windows·Ollama 환경에서 로컬 `ollama create`·질문/임베딩 동작을 먼저 검증한 뒤 반입한다. 서버에서도 로컬 파일로 모델을 등록하고 `ollama ls`와 시험 요청으로 확인한다. 설계상 첫 후보는 `qwen3:4b`와 `qwen3-embedding:0.6b`에 해당하는 모델이며, 파일 형식·양자화·모델 이름과 품질을 확인해 최종 확정한다.
3. Ollama API가 서버 PC의 `localhost:11434`에서 응답하는지 확인한다. Ollama 포트는 내부망 사용자에게 직접 개방하지 않는다.
4. Windows용 일반 설치 프로그램은 사용자 계정에서 백그라운드 실행된다. 로그인하지 않은 상태에서도 상시 운영해야 한다면 Ollama 공식 문서의 독립 실행 CLI와 서비스 연동 방법을 검토하고, **재부팅 후 로그인 없이 API가 응답하는지** 설치 완료 조건으로 시험한다.

### 4.4 서버 폴더와 운영 설정

1. `C:\CaseSearch\data\incoming`, `originals`, `evaluation`, `config`, `backups`, `logs`, `releases`를 만든다. 드라이브 문자는 실제 저장 공간에 따라 바꿀 수 있다.
2. 비밀값이 없는 운영 설정에 입력·보관 폴더, 매일 검사할 시각, 웹 포트, DB 주소, 모델 이름을 기록한다. 공통 문서 암호와 DB 비밀번호는 서버의 비공개 환경변수 또는 접근 권한을 제한한 별도 비밀 설정에 보관한다. Git과 `release/`에는 넣지 않는다.
3. 운영 계정에 필요한 폴더만 읽기·쓰기 권한을 준다. 문서 원본, 질문·답변 기록, 평가 Excel, 백업 파일은 일반 웹 사용자가 파일 경로로 직접 열 수 없게 한다.
4. <span style="color:red">Windows 방화벽에서는 확정된 웹 포트만 허용된 내부망 주소 대역에 개방한다. PostgreSQL과 Ollama는 로컬에서만 사용한다. 실제 서비스 시작 전에 로그인 방식과 계정 연계, 일반 사용자·관리자 권한, 질문·원문 열람 범위와 다른 사용자 질문 요약의 익명화·마스킹 규칙을 확정한다. 로그인하지 않은 사용자는 질문·대기열·결과를 조회할 수 없게 한다.</span>
5. 앱·브라우저 화면·Ollama에 인터넷 목적지나 원격 분석·원격 모델 호출을 설정하지 않는다. 폐쇄망에서 앱을 실행해 외부 연결 없이 화면, 검색, 답변, 문서 등록이 완료되는지 확인한다.

## 5. 첫 배포

1. 개발 PC에서 공개·가상 자료로 검증한 `release/`를 Git 추적 바깥에 생성한다. 앱 코드·`docs/` 화면·고정 의존성 목록·DB 변경 파일·설정 예시가 모두 있는지 확인한다. 전송 폴더의 `wheelhouse/`와 설치 파일·모델 파일을 함께 목록화한다. 개발용 가상환경, 실제 원본·평가·로그·백업, 비밀값은 포함하지 않는다.
2. 전송 묶음을 기관 절차로 반입하고 서버에서 SHA-256을 대조한다. 그중 `release/` 전체를 새 버전 폴더(예: `C:\CaseSearch\releases\v1.0.0\`)로 복사한다. 웹 화면만 있는 `docs/` 단독 복사는 배포로 간주하지 않는다. 배포 버전과 빌드 시각을 기록한다.
3. 서버에서 `py -m venv 'C:\CaseSearch\releases\v1.0.0\.venv'`로 가상환경을 만든다. 그 가상환경의 Python으로 `pip install --no-index --find-links`와 반입한 `wheelhouse/`, 해당 버전의 `requirements.txt`를 지정해 오프라인 설치한다. 누락 패키지가 있으면 인터넷 접속을 시도하지 않고 반입 묶음을 다시 준비한다.

4. DB 백업이 확보된 상태에서 해당 버전에 포함된 DB 변경 파일을 적용한다. 실패하면 서비스를 시작하지 않고 원인을 확인한다.
5. 운영 설정과 비밀값을 서버에서 연결한다. FastAPI/Uvicorn이 `release/docs/`와 `/api`를 제공하도록 시작한다. 답변 작업자는 서버 전체에서 1개만 실행하고, 여러 웹 프로세스가 작업자를 중복 생성하지 않도록 한다. 실제 실행 명령과 시작 스크립트 이름은 구현 때 확정한다.
6. 초기 동작 확인을 마친 뒤 Windows 작업 스케줄러 또는 서비스 관리 방식으로 앱의 자동 시작과 오류 후 재시작을 설정한다. Ollama와 DB가 먼저 준비되어야 하며, 재부팅 후 사용자 로그인 없이 웹 화면·`/api`·Ollama·DB 연결이 복구되는지 시험한다.

## 7. 후속 버전 배포와 되돌리기

1. 현재 버전, DB 구조 버전, 모델·색인 버전과 백업 시각을 기록한다. 새 질문 접수를 잠시 멈추고 진행 중인 답변 작업이 끝나거나 안전하게 재개 가능한 상태가 될 때까지 기다린다.
2. PostgreSQL과 원본·평가 Excel·운영 설정을 폐쇄망 안에서 백업한다. 승인된 오프라인 전송 묶음의 해시를 확인한 뒤 새 `release/`를 기존 폴더 위에 덮어쓰지 않고 새 버전 폴더에 복사한다. 백업과 운영 로그를 외부망으로 가져가지 않는다.
3. 새 버전 폴더의 `.venv`를 만들고 반입한 `wheelhouse/`에서만 의존성을 설치한다. 필요한 DB 변경을 적용한 뒤 실행 대상을 새 버전으로 바꾸고 서비스를 다시 시작한다.
4. 6장의 접속·검색·대기열·문서 등록 핵심 항목을 확인한다. 문제가 있으면 이전 버전으로 실행 대상을 되돌린다. DB 변경이 이전 앱과 호환되지 않으면 사전에 마련한 복구 절차에 따라 백업을 복원한다.
5. 배포 결과, 실패 사유, 적용·복구 시각을 기록한다. 데이터 폴더와 비밀 설정은 버전 교체 과정에서 삭제하거나 덮어쓰지 않는다.

## 8. 백업 대상과 미정 사항

백업에는 PostgreSQL DB, 보관 원본, 향후 승인된 평가 Excel과 변경 후보, 운영 설정과 비밀값의 안전한 보관본을 포함한다. Ollama 모델과 Python 가상환경은 재설치 가능하지만, 재설치에 필요한 모델 이름과 패키지 버전은 기록한다. 백업 파일은 운영 파일과 다른 저장 위치에 두고 복구 시험을 주기적으로 실시한다.

백업과 복구 시험은 폐쇄망 안에서 수행한다. 실제 사용자 질문·답변·피드백, 검색 색인·임베딩, 평가 파일, 로그·오류 보고서도 운영 자료로 분류해 외부 개발 PC·GitHub·공개 웹페이지로 내보내지 않는다. 외부망 개발·시험에는 공개 또는 가상 자료만 사용한다.

<span style="color:red">구현 전에 서버의 실제 드라이브와 여유 공간, 내부 주소·포트, 설치 버전, 로그인·계정 연계 방식, 일반 사용자·관리자 권한, 질문·원문 열람 범위, 질문 요약의 익명화·마스킹 규칙, 일일 검사 시각, 백업 주기·보존 기간, 자동 시작 방식, 승인된 반입 절차와 모델 파일의 로컬 등록 방법을 확정해야 한다. pgvector의 Windows 오프라인 설치 방법은 서버와 동일한 시험 환경에서 미리 확정·검증한다. 최종 설치 절차에는 사전 검증된 파일명·버전·해시·오프라인 명령과 실제 서버의 최종 확인 결과를 추가한다.</span>
