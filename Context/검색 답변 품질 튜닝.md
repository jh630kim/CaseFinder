# 검색·답변 품질 튜닝

## 1. 목적과 범위

사용자의 자연어 질문에 적절한 사건을 찾고, 사건의 일치점·차이점과 원문 근거를 정확하게 설명하도록 검색·답변 설정을 개선한다. 여기서 튜닝은 문서 추출·분할, 검색 순위, 근거 선택, 답변 지침과 생성 옵션의 조정이다. 모델 가중치를 추가 학습하는 파인튜닝은 현재 범위에 포함하지 않는다.

설정값은 이 문서의 제안을 곧바로 확정하지 않는다. 제공된 PDF와 추후 HWPX 샘플로 대표 질문을 만들고, 변경 전후 결과를 비교해 선택한다. 자동 개선은 사용자가 질문하는 동안 GPU를 점유하지 않도록 이용이 적은 시간에 실행하는 방안을 우선 검토한다.

<span style="color:red">튜닝 평가와 재색인은 답변 작업과 GPU를 공유한다. 공통 작업 조정 기능에서 사용자 질문의 임베딩·답변을 우선 처리하고, 평가·재색인은 배치 단위 사이에 양보한 뒤 이어서 실행한다. 작업 상태와 이어서 실행할 위치를 기록한다.</span>

## 2. 품질 문제를 먼저 분류한다

| 보이는 문제 | 먼저 확인할 지점 | 가능한 조정 |
| --- | --- | --- |
| 원문에 있는 사건이 검색되지 않음 | 문서 추출, 사건 경계, 색인 누락 | 재추출·재색인, 문단 분할, 검색 후보 수 |
| 관련 없는 사건이 상위에 나옴 | 핵심 조건 인식, BM25·임베딩 순위 | 조건 비교, RRF 결합 설정, 후보 재정렬 |
| 맞는 사건인데 중요한 차이를 놓침 | 사실관계 묶음, 부정 표현, 답변 지침 | 사건 대표 묶음, 조건 비교, 출력 형식 |
| 답변 내용이나 인용이 틀림 | 전달된 원문 근거, 원문 위치, 생성 설정 | 근거 선택, 답변 지침, 생성 옵션 |
| 답변이 지나치게 늦음 | 검색·모델 실행 시간, 문맥 길이 | 후보 수, 전달 근거량, `num_ctx`, 모델 후보 |

## 3. 조정 가능한 항목과 첫 시험안

| 영역 | 조정 항목 | 첫 시험안과 판단 기준 |
| --- | --- | --- |
| 문서 정리 | 사건 경계와 본문 구획 | 책자 전체를 한 건으로 저장하지 않고 사건별로 분리한다. 다른 사건이 한 묶음에 섞이면 실패로 본다. |
| 임베딩 입력 | 사건 대표 묶음·근거 문단 길이 | 제목·사실관계와 결정 근거를 구분하고, 문단은 문장 경계를 지키며 약 300~500토큰부터 시험한다. |
| 임베딩 질문 | 검색 목적 지시문 | Qwen3 임베딩 후보의 질문 지시문 사용 여부를 같은 대표 질문으로 비교한다. |
| 검색 | BM25·임베딩 후보 수와 RRF 결합 | 기대 사건의 검색 여부와 중요한 조건의 일치율을 비교해 조정한다. |
| 조건 확인 | 사건번호, 인명·대물 사고 유무 등 | 명시된 조건을 임베딩 유사도와 별도로 확인하고 불일치를 답변에 표시한다. |
| 답변 지침 | 출력 형식·근거 사용 규칙 | 사건번호·내용·결정·유사점·차이점·원문 위치를 요구하고, 근거 없는 내용을 단정하지 않게 한다. |
| 생성 옵션 | `temperature`, `num_ctx`, 출력 길이 | `temperature` 약 0.1, `num_ctx` 4,096부터 시험한다. 근거가 잘리면 문맥 길이를 조정하고 VRAM·시간을 측정한다. |

위 숫자는 성능 보증값이 아닌 출발값이다. 임베딩 모델·차원·입력 형식이 바뀌면 이전 벡터와 섞지 않고 필요한 문서를 다시 임베딩한다. 모델 및 설정 버전을 검색 결과에 함께 기록한다.

## 4. 자동으로 할 수 있는 일과 사람이 개입할 일

| 단계 | 시스템·AI가 자동으로 처리 | 사용자·담당자가 개입해야 하는 경우 |
| --- | --- | --- |
| 결과 평가 수집 | 질문, 제시된 사건, 클릭·평가, 당시 설정·색인 버전을 기록 | 사용자는 적절함·부적절함을 표시하고, 가능하면 문제 유형이나 기대 사건번호를 알려준다. |
| 원인 진단 | 누락 사건의 색인 유무, 조건 충돌, 인용 위치 오류, 응답 시간을 검사하고 문제 유형을 추정 | 평가 자체가 틀렸거나 사건의 법적 의미가 애매하면 담당자가 원문을 확인한다. |
| 문서 오류 처리 | 원본에서 재추출·재분리·재색인을 시도하고 결과를 원문과 대조 | 암호 해제 실패, 표·스캔 이미지, 불명확한 사건 경계처럼 원문 사실을 확정할 수 없을 때만 확인한다. |
| 변경안 생성 | 문단 길이, 검색 후보 수·순위 결합, 근거 선택, 답변 지침의 제한된 변경안을 만든다 | 새 문서 유형의 해석 규칙이나 답변 정책을 바꾸어야 할 때 방향을 정한다. |
| 변경안 평가 | 관리자가 승인한 버전의 대표 질문을 다시 실행해 검색 적중, 조건 불일치, 원문 인용, 응답 시간의 전후 차이를 계산한다. | AI가 만든 질문·기대 사건·근거 초안을 검토·승인하고, 자동 판정이 어려운 의미 오류를 표본 검토한다. |
| 운영 반영 | 미리 정한 통과 기준을 만족하는 낮은 위험의 설정 변경을 반영하고 이전 버전을 보관한다. 기준 미달이면 보류하거나 이전 버전으로 되돌린다 | 기준을 바꾸거나, 모델 교체·대규모 재색인처럼 영향이 큰 변경을 채택할 때 검토한다. |

사용자 평가 한 건을 정답으로 간주해 즉시 검색 설정을 바꾸지 않는다. AI가 작성한 답변을 AI의 자체 평가만으로 합격시키지도 않는다. 원문과 일치하는 인용 여부, 기대 사건의 검색 여부처럼 확인 가능한 기준을 우선 사용한다. 사람이 모든 피드백을 수작업으로 고치는 방식도 요구하지 않는다.

## 5. 시스템에 반영되는 과정

```text
사용자의 질문·평가 수집
          ↓
문제 유형 자동 진단 → 원문 확인이 필요한 건만 담당자에게 표시
          ↓
검색·답변 변경안 생성 및 별도 버전으로 저장
          ↓
대표 질문의 기존 결과와 변경안 결과 비교
          ├── 기준 통과 → 운영 설정 적용·이전 버전 보관
          └── 기준 미달 → 변경 보류·실패 원인 기록
          ↓
운영 중 품질 저하 감지 시 이전 버전으로 되돌리기
```

자동 적용 대상은 미리 허용한 범위의 검색·답변 설정으로 제한한다. 문서 원문이나 사건의 사실관계를 AI가 임의로 바꾸지 않는다. 변경 전후의 질문·검색 후보·답변·근거·처리 시간·설정 버전을 함께 보관하여 비교와 복구가 가능하도록 한다.

## 6. 대표 질문과 통과 기준

대표 질문에는 질문 문장, 기대 사건번호, 반드시 맞아야 하는 사실관계, 허용 가능한 원문 근거를 기록한다. 음주·인명사고 없음·대물사고 있음처럼 조건 조합이 중요한 사례와 관련 사례가 없는 질문을 모두 포함한다. 사용자 평가에서 검증된 새 사례를 추가하되, 기대 답은 원문과 대조한다.

자동 비교 항목은 기대 사건의 상위 결과 포함 여부, 핵심 조건 불일치, 인용한 원문·위치의 존재 여부, 답변 누락 항목, 응답 시간과 오류율이다. 설명의 법적 타당성이나 미묘한 사실관계는 자동 점수만으로 확정하지 않는다. 통과 기준의 수치와 자동 변경 범위는 대표 질문을 구축한 뒤 정한다.

### 6.1 통합 Excel 질문·정답지의 지속 갱신과 관리자 승인

DB의 실제 사용자 질문·시스템 답변·사용자 평가는 검색·답변 설정을 개선하는 튜닝 자료로 사용한다. Excel의 질문·정답과 관리자 승인 상태는 평가 자료로 분리한다. 승인 정답은 검색 색인이나 실제 사용자 답변 프롬프트, 변경안 생성의 정답 입력에 넣지 않는다. 승인 질문을 실행한 결과와 기대 정답을 평가 단계에서만 비교한다.

질문과 기대 사건·근거는 하나의 `.xlsx` 파일에서 문항 ID로 연결해 관리한다. AI가 등록 문서에서 최초 초안을 만들고 이후 DB의 사용자 피드백으로 추가·수정·삭제 후보를 계속 쌓는다. 각 후보에는 이전 승인본과 제안본의 질문·정답, 달라진 항목, 변경 이유, 원문 근거 위치, 관련 피드백과 예상되는 평가 영향을 함께 기록한다. 후보가 이미 승인된 평가본을 자동 변경하지 않는다.

관리자가 원할 때 시스템은 통합 Excel 파일의 승인본과 후보를 항목별로 비교한 보고서를 화면 또는 같은 파일의 보고 시트에 제시한다. 신규 후보는 이전 값이 없음을, 삭제 후보는 삭제할 기존 값을 표시한다. 관리자는 질문과 정답을 한 쌍으로 검토해 승인·수정·반려한다. 승인자·시각·버전을 기록하고 승인된 버전만 튜닝 평가에 사용한다. 승인본이 없으면 자동 반영의 합격 판정을 내리지 않는다.

## 7. 개발 시 필요한 구성

- 결과 화면의 평가 입력: 적절함·부적절함, 문제 유형, 선택적 기대 사건번호.
- 평가·질문·검색 결과·근거·모델·색인·설정 버전의 기록.
- 대표 질문을 보관하고 변경 전후를 같은 조건으로 재실행하는 평가 작업.
- 변경안 생성·시험·적용·보류·되돌리기의 상태 관리와 이력 화면.
- 원문 확인이 필요한 건만 담당자에게 모아 보여주는 확인 목록.
- 자동 개선 작업의 실행 시각과 답변 작업자와의 자원 충돌 방지.
